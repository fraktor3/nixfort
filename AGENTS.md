# AGENTS.md — правила для ИИ-исполнителя (Cursor)

> **Текущая роль Cursor (ADR-018): инженер стенда.** Основной код пишет архитектор. Ты выполняешь карточки `docs/tasks/S-xxx-*.md`: разворачиваешь код на ВМ стенда (`ssh nx-controller` и т.д.), запускаешь проверки, сохраняешь фактический вывод в `lab/reports/`, сообщаешь о расхождениях. **Код в `app/` и `agent/` не меняй**, если карточка или архитектор прямо этого не поручили — опиши проблему и приложи вывод. Все правила ниже по-прежнему действуют.

Ты — **исполнитель** в проекте NIXFORT. Архитектуру, объём и приёмку определяет архитектор (Claude) и руководитель проекта (человек). Твоя задача — качественно реализовать **ровно одну карточку задачи** из `docs/tasks/`.

## 1. Перед любой работой прочитай (в этом порядке)
1. `docs/PROJECT_CONTEXT.md` — что за проект, стек, границы.
2. `docs/STATUS.md` — где мы сейчас, текущая задача.
3. Карточку текущей задачи `docs/tasks/T-XXX-*.md`.
4. Разделы `docs/ARCHITECTURE.md`, на которые ссылается карточка (и `docs/NODE_AGENT_PROTOCOL.md` / `docs/CHECKS_CATALOG.md`, если задача их касается).
5. `docs/SECURITY.md` — обязательно, если задача касается агента, выполнения команд, SSH, firewall, загрузки файлов, прав доступа.

Сверь `STATUS.md` с `git log --oneline -15` и фактическим кодом. Если есть расхождение — **сообщи**, не угадывай.

## 2. Порядок работы над задачей
1. **Plan:** перескажи задачу своими словами (3–5 строк), перечисли файлы, которые создашь/изменишь, и тесты. Дождись подтверждения.
2. **Implement:** пиши код только в пределах карточки. Не трогай несвязанные модули.
3. **Test:** напиши тесты из карточки, запусти их, покажи фактический вывод.
4. **Report:** в конце сообщи: изменённые файлы; что сделано; какие критерии готовности выполнены; какие тесты запускались и их фактический результат; что не сделано/не проверено; риски.
5. **Update:** обнови `docs/STATUS.md` (раздел «Журнал» + «Текущая задача»). Если менялся контракт/модель — обнови соответствующий документ.

## 3. Запрещено (нарушение = задача не принимается)
- `shell=True`, `os.system`, `os.popen`, `eval`, `exec`, `pickle` с недоверенными данными, сборка командной строки через f-строки/конкатенацию.
- Любая функция «выполнить произвольную команду». Внешние программы запускаются только через `subprocess.run([...список аргументов...], timeout=..., check=False)` из модулей-адаптеров, аргументы — константы или валидированные значения.
- Отключение проверки SSH host key (`AutoAddPolicy`, `StrictHostKeyChecking=no`), отключение проверки TLS.
- Секреты, пароли, ключи в коде, тестах, логах, фикстурах, git. Только `.env` (не коммитится) / файлы секретов.
- Пустые `except:` / `except Exception: pass`. Ошибка должна стать понятным статусом (`ERROR`/`UNKNOWN`) с безопасным `error_code`.
- Статус успеха (`PASS`, `SUCCEEDED`, `VERIFIED`) без фактического подтверждения. Нет данных → `UNKNOWN`. Сбой → `ERROR`.
- Заглушки, которые «делают вид» (константный `return True`, фиктивные проверки) без явной пометки `TODO(T-XXX)` и упоминания в отчёте.
- Новые зависимости без указания в отчёте и причины. Новые функции «на будущее».
- Изменение архитектуры, моделей данных других модулей, протокола агента — без согласования. Если карточка этого требует неявно — остановись и спроси.

## 4. Стиль кода
- Python 3.12, Django 5.2. Типизация (type hints) для публичных функций. `ruff` (lint + format), `mypy` для `agent/` и `app/apps/*/services`.
- Бизнес-логика — в `services.py` / `domain.py` модуля, не во views/templates/models.save().
- Оценка проверок — **чистые функции** без I/O (`evaluate(facts, ctx) -> CheckOutcome`), чтобы их тестировать на фикстурах.
- Время — UTC в БД. Идентификаторы — UUID.
- Имена: код и идентификаторы на английском, интерфейс и сообщения пользователю — на русском.
- Любой запуск внешней программы: таймаут, ограничение размера вывода, проверка кода возврата, нормализация ошибки.

## 5. Тесты
- `pytest` + `pytest-django`. Локально (Windows): `pytest -m "not integration"` на SQLite (`config.settings.test`).
- Интеграционные (`@pytest.mark.integration`) — на контроллер-ВМ с PostgreSQL/Redis/реальными узлами.
- Для каждой проверки — фикстуры минимум на PASS, FAIL, UNKNOWN (+ERROR где применимо).
- Для каждого входного поля, попадающего в агент/внешний инструмент, — тест на инъекцию (`; | & $( ) \` \n ../`).
- Никогда не пиши «тесты прошли», если не запускал их и не видел вывод.

## 6. Новый чат
Одна задача — один чат. Если контекст потерян: перечитай раздел 1 и продолжи с `docs/STATUS.md`. Не переделывай принятые задачи.
