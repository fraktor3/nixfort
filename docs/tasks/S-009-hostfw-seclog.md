Что нового: проверка **HFW-01** (хостовый межсетевой экран на сервере) и шаг плана «Хостовый межсетевой экран сервера» (nftables input-only: открыты только заявленные порты + SSH с контроллера). Страница проекта **«Журналы безопасности»** (неудачные входы по SSH + баны Fail2ban + события IDS). Агент обновляется до **1.6.0**.

## Часть A — обновление (Cursor)
1. nx-controller: `cd ~/nixfort && git pull && make up` → `make selfcheck` → `make itest` (ожидается 443 passed, 5 skipped, 0 failed).
2. Агент на трёх узлах → `agent_version":"1.6.0"`.
3. На сервере только чтение: `ssh labadmin@10.77.0.30 'which nft; sysctl net.ipv4.ip_forward; sudo nft list ruleset | head -5; sudo journalctl _COMM=sshd --since -24h -q | tail -3'`. Если `nftables` на сервере нет — часть B установит его сама (шаг плана), это нормально.
4. Снимок всех четырёх ВМ **`lab-s009-before`**.

## Часть B — хостовый межсетевой экран на сервере (нажимает Cursor под `cursor`; шаги под `viewer1` — руководитель)
5. «Инвентаризация всех узлов» → «Аудит» → «Запустить аудит». На **nx-server** ожидается новая проверка **HFW-01 — FAIL** («Хостовый межсетевой экран не настроен»). Остальное — как в предыдущих приёмках. Скриншот строки HFW-01.
6. «Сформировать план исправлений» (флажок ключа не ставить). Среди шагов nx-server ожидается **«Хостовый межсетевой экран сервера: открыты порты [80] и SSH с 10.77.0.10, …»** (если nftables не установлен — перед ним шаг установки nftables). Скриншот плана.
7. «Утвердить и выполнить». Ожидается «Применён и подтверждён»; HFW-01 → PASS. Постпроверка идёт через **новое SSH-соединение** с сервером (`nft.inspect`): если бы правила отрезали управление — был бы автооткат. Скриншоты задания и «до/после».
8. Cursor на сервере (только чтение): `sudo nft list table inet nixfort` — цепочка input с `policy drop`, `tcp dport { 80 }` (или ваши заявленные порты) и `ip saddr { 10.77.0.10, … } tcp dport 22 accept`. Проверить, что сервис на 80 доступен с клиента: `ssh labadmin@10.77.0.40 'curl -s -m2 -o /dev/null -w "%{http_code}\n" http://10.99.0.10/'` (ожидается ответ, не таймаут). С Windows `ssh nx-server hostname` — работает.
9. Проверить, что ЗАКРЫТЫЙ лишний порт теперь недоступен снаружи: с клиента `nc -zv -w3 10.99.0.10 8080` — таймаут/отказ (раньше SYS-04 показывал 8080 открытым; хостовый экран его закрыл для сети). На самом сервере порт может слушаться, но снаружи закрыт.

## Часть C — журналы безопасности (нажимает Cursor под `cursor`; шаги под `viewer1` — руководитель)
> **Повтор с шага 10** (после остановки 27.10). Хостовый экран сервера из части B — НЕ откатывать. Сначала `git pull && make up && make itest` на nx-controller (ожидается **445 passed, 5 skipped, 0 failed**; агенты не обновлять — версия прежняя, 1.6.0).

10. «Проверка защиты» → «Подбор пароля SSH» → «Запустить». Ожидается вердикт **«Защита сработала»** и уровни:
    - «Межсетевой экран (шлюз)» — сработал (до sshd 0 из 6);
    - «Suricata (шлюз)» — сработал (sid 9000003);
    - **«Хостовый межсетевой экран (сервер)»** — сработал: «дошли до sshd: 0 из 7; не установлены: 7» (клиент 10.77.0.40 не входит в разрешённые источники SSH);
    - «Fail2ban (сервер)» — «нет данных»: «не потребовался: попытки остановил хостовый межсетевой экран до sshd». Это правильно: Fail2ban был проверен в S-006 без хостового экрана, теперь атаку останавливает более ранний уровень.
    Скриншот.
10a. Создать неудачные входы с **разрешённого** источника, чтобы было что анализировать в журналах. На **nx-controller** (адрес 10.77.0.10 разрешён хостовым экраном и стоит в `ignoreip` Fail2ban — бана не будет):
    `for u in a b c; do ssh -o BatchMode=yes -o ConnectTimeout=5 nixfort-demo-$u@10.77.0.30 true; done`
    Ожидается три раза `Permission denied`. Если ssh спрашивает про ключ узла — сверить отпечаток с `SHA256:yVN00FXcdGV9qAdk97PMAKoN5/j1lH3bL5KPSDhk4ak` (из S-008) и только при совпадении принять. С Windows (10.0.2.2) так не делать — этот адрес Fail2ban может забанить.
11. Проект → «Журналы безопасности» → «Обновить сводку». Ожидается:
    - по **nx-server**: неудачных входов SSH **≥ 3**, источник **10.77.0.10**, имена `nixfort-demo-a/b/c`; Fail2ban — служба active, в бане никого (контроллер в `ignoreip`);
    - блок «События обнаружения вторжений»: sid 9000003 и 9000002 с количествами.
    Скриншот.
12. Под `viewer1`: страница «Журналы безопасности» открывается, кнопки «Обновить сводку» нет.

## Часть C2 — запись трафика во время нагрузки (T-025, нажимает Cursor под `cursor`)
13. «Проверка защиты» → карточка «Проверка устойчивости под нагрузкой» → «Запустить». Отдельно запускать запись не нужно: сценарий сам записывает интерфейс датчика шлюза (enp0s9, 22 с) параллельно с нагрузкой. Задание идёт примерно 35–45 с.
14. Ожидается: вердикт «Защита сработала» (как в S-008: 80 доступен, 8080 поглощён экраном, Suricata sid 9000002). При включённом хостовом экране сервера из части B — то же самое. На странице проверки — блок **«Трафик на шлюзе во время проверки»**: число пакетов (сотни), график «Пакеты и новые соединения» с выраженным всплеском, находка **«Всплеск попыток TCP-соединений»** от 10.88.0.10 (порты 80, 8080), ссылка «полный разбор». Эта же запись появляется в разделе «Трафик». Скриншоты блока и полного разбора.
15. Если блок пишет «Запись трафика не получена: …» — вердикт при этом не должен меняться; причину из блока и журнал задания — в отчёт, остановиться.
16. Сразу после: `ssh nx-server "uptime; systemctl is-active ssh"` — сервер жив; на шлюзе `sudo ls -la /var/lib/nixfort/tmp` — пусто.

## Часть D — автооткат хостового экрана (необязательно, если есть время)
17. На сервере вручную (как в прошлых карточках, ключ контроллера во временной копии) отправить `nft.apply_host_firewall.v1` с `management_sources` БЕЗ контроллера (например только `10.77.0.99`) и `rollback_timeout_s` 30, без commit. Сразу новое SSH на сервер должно пропасть, через ≤60 с вернуться (узел сам откатил). Подтвердить `mutation.snapshot_status.v1` → `rolled_back: true`. Удалить временный ключ.
